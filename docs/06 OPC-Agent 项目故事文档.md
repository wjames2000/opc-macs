## 序章：一个人的公司

---

Alex 看了眼手机上的时间，凌晨 1:47。

三小时前，他刚推送了 SaaS 工具的新版本。本来打算发完版本就去睡，但一封用户投诉邮件让他打开了电脑，然后又被明天的产品推广文案拽住了。

这不是偶发事件。自从去年裸辞做独立开发者以来，这是第无数个这样的夜晚。产品迭代、营销文案、客户邮件、财务对账、合同审查——他一个人扛着一支完整团队的活。产品越做越好，用户越来越多，但他的睡眠时间却越来越少。

Alex 不是个例。2026 年，全国超 1200 万个体创业者正经历着同样的困境。政策在喊"单人成军"，资本在追捧"超级个体"，但没人告诉他们——一个人怎么支撑起一家公司。

故事从这里开始。

## 第二章：一丝微光

### 偶然的发现

某个深夜，Alex 在 Hacker News 上看到了一篇关于 Google ADK Go 的文章。"Agent Development Kit for Go"——这个标题让他多看了几秒。

他一直在用各种 AI 工具单点提效：ChatGPT 写文案、Claude 审代码、Gemini 分析数据。但这些工具各自为战，没有形成一个系统。他需要的是——一个能用自然语言指挥的 AI 团队，帮他处理那些重复性高、规则明确的业务任务。

ADK Go 的 code-first 理念击中了他。不是用提示词堆砌一个脆弱的 AI 应用，而是用 Go 代码定义 Agent 的职责边界、执行流程和输出契约——版本可控、可测试、可复用。

更重要的是：**Go 静态编译，单二进制部署**。他不需要维护一个复杂的 Python 环境，不需要 Docker Compose，不需要 GPU。一个可执行文件，就能跑起一整个 AI 团队。

### 灵感的碰撞

但如果只是把几个 AI 拼在一起，那不是他想要的。Alex 过去踩过太多坑：Agent 经常越界做不该做的事、大模型输出格式飘忽不定、对话上下文越聊越臃肿、token 消耗和成本一起飞涨。

他需要的是四个能力：

1. **角色边界**——每个 Agent 只做一件明确定义的事，不越权、不跑偏
2. **状态机**——执行步骤有约束，不会跳过关键环节，也不会陷入死循环
3. **产物契约**——Agent 之间不靠对话记忆传递信息，而是用结构化 JSON 做契约
4. **护栏规则**——有明确的禁止清单和人机确认机制，防止安全事故

他管这个叫 **Harness（驾驭系统）**——一套给 Agent 套上的"马具"，让强大的 AI 能力在可控的轨道上运行。

### 技能的启示

还有一个问题：Agent 的能力越多，上下文提示词就越膨胀。一个会写文案、会分类邮件、会审代码的 Agent，启动时把所有指令都塞进去的话，每次调用都在燃烧 token——也是燃烧他的利润。

然后他看到了 ADK 的 **Skill 渐进式披露**机制：

> L1（发现层）——启动时只加载技能名称和 30 字简述
> L2（激活层）——任务匹配时才注入完整指令
> L3（引用层）——执行中按需加载参考资源

这个设计的优雅之处在于：它把"给 Agent 喂知识"这件事从 OCaml 式的一次性加载变成了按需流式加载。实测 10 个技能的场景下，基线上下文从 10,000 tokens 降到了约 1,000 tokens——**节省了 90%**。

对于 Alex 这样每 1 元 token 成本都是利润的 OPC 创业者来说，这 90% 就是竞争力。

### 最后的拼图

还有一个始终困扰他的问题：**系统会忘记**。

今天的 Agent 不知道昨天做了什么决定。用户今天的偏好和昨天的设定对不上。每次任务都是"全新开始"——这意味着同样的错误会反复犯，同样的信息要反复说。

他需要的是一套**记忆系统**——让 Agent 在工作结束后把关键信息记下来，下次再有类似任务时自动调取参考。

但 MVP 阶段不能上 Postgres + pgvector，太重了。他选择了一个更轻巧的方案：**嵌入式向量记忆引擎**。

- 每次任务完成后，生成 embedding，存到本地 JSON 文件
- 新任务启动时，自动检索相似历史记忆并注入上下文
- 接口抽象，未来可无缝切换 pgvector

这个选择意味着：MVP 第一天起，系统就在"成长"。每一次对话都在让下一条输出变得更好。

## 第三章：系统诞生

### 架构愿景

Alex 在纸上画出了系统的骨架：

```

       你的一句话指令
              │
              ▼
      ┌──────────────┐
      │  Router Agent │ ← 判断你要干什么
      │  (意图识别)   │
      └──────┬───────┘
         ┌───┴───┐
         ▼       ▼
    ┌────────┐ ┌────────┐      ┌──────────────┐
    │ 文案助手 │ │ 邮件助手 │ ... │ 未来更多插件  │
    │ (.so)  │ │ (.so)  │      │ (.so)        │
    └────┬───┘ └────┬───┘      └──────┬───────┘
         │          │                 │
         └────┬─────┴─────────┬───────┘
              ▼
      ┌──────────────┐
      │  Reviewer    │ ← 质量把关，独立公正
      │  (审查)      │
      └──────┬───────┘
             ▼
      ┌──────────────┐
      │  HITL 确认    │ ← 敏感操作，人工终审
      └──────┬───────┘
             ▼
      ┌──────────────┐
      │  Memory      │ ← 记住每次交流，越来越懂你
      │  (记忆存储)   │
      └──────────────┘
             ▼
          输出结果
```

每个业务 Agent 都是独立的 .so 插件——新增一个 Agent 只需要写一个插件并编译，主程序完全不用动。这意味着：其他 OPC 开发者可以分享他们的 Agent 插件，Alex 可以直接下载使用。

### 第一个 MVP 的边界

Alex 给自己定了一个铁律：**两周内跑通闭环**。

MVP 范围被他刻意压缩到了最小：

| 必须做 | 绝不做 |
|--------|--------|
| Router + 插件加载器 + 3 个 Agent 插件 + Reviewer | Postgres/pgvector（用嵌入式引擎替代） |
| 文案生成 .so + 邮件分类 .so + 小红书 .so | Docker 容器化部署 |
| Harness 四要素落地 | 独立 Web 前端 |
| HITL 终端交互确认 | A2A 跨 Agent 协议 |
| 嵌入式向量记忆引擎 | 外部 API 真实集成 |
| 控制台可观测性 | 多用户、权限系统 |
| Plugin 热加载（重启生效） | 生产级安全认证 |
| token 消耗统计 | — |

### 两周的节奏

```
第 1-2 天  环境就绪：ADK Go 跑通 demo，Harness 概念验证
第 3-6 天  两个业务 Agent 独立完成：文案 + 邮件分类 + Skill 文件
第 7-9 天  端到端闭环：串联 Router → Agent → Reviewer → HITL → Memory
第 10-14 天 打磨验证：测试、修复、写验证报告
```

两周后，他就可以跟自己的 AI 团队"对话"了。

## 第四章：全新的一天

### Alex 的一天（使用后）

```
08:00 打开电脑，输入"处理昨天的邮件"
      → 系统自动分类 35 封邮件，标记了一封紧急投诉，生成了回复草稿
      → Alex 快速审阅，点击确认，10 分钟搞定

09:00 输入"帮我写智能水杯的新品文案，风格要科技简约"
      → Agent 根据上个月成功的那篇文案的风格偏好，生成了三段文案
      → Reviewer 检查：无禁止词，格式规范，评分 4.8/5.0
      → Alex 微调了一行，确认发布

10:00 进入研发时间，专注写代码——没有被打断

14:00 输入"分析今天客户的退款原因"
      → Agent 检索了过去一周所有退款相关记录
      → 发现是因为新版本的一个 UI 问题
      → Alex 紧急修复，减少了可能的更多退款

17:00 系统弹出提示："今日 token 消耗：1,250 个，约 ¥0.08"
      → Alex 笑了笑：一杯矿泉水的钱，省了半天的活

18:00 准时收工。去跑步。
```

- 全国超 **1,200 万**个体创业者选择"个人决策 + AI 执行"模式
- 华为等科技巨头正式入场 OPC 产业赋能
- 超过 **20 个城市**出台 OPC 专项扶持政策

HACR（人机成本比）基准显示：**每投入 1 元 AI 成本，等效替代约 72 元人力支出**。

OPC-Agent 不是要做一个大而全的商业平台，而是为像 Alex 这样会写 Go 的 OPC 创业者提供一个**高度可定制、数据自主可控、长期成本极低**的智能协助系统基座。

## 尾声：每个超级个体的起点

OPC-Agent 不是一个"什么都能做的 AI 平台"。它是一套**你可以掌控的 AI 团队操作系统**。

它的设计哲学只有一句话：

> **约束设计，而非原始模型能力，才是 AI 在复杂系统中扩展的关键。**

不需要让 Agent 无所不能。只需要让它在你需要的地方，做到极致。

Alex 的故事还在继续。今天他省下了处理邮件和写文案的时间，用在了产品功能开发上。明天他可能会给 OPC-Agent 加上一个新的 Skill——竞品监控，或者财务自动对账。每一个新 Skill，都让他离"一个人管理一家公司"这个目标更近一步。

**你的故事，也可以从这里开始。**
