# 多任务智能协助系统（OPC-Agent）——项目需求说明书

> **版本**：v1.1  
> **日期**：2026-05-09  
> **目标用户**：具备 Go 开发能力的 OPC（一人公司）创业者  
> **项目代号**：OPC-Agent  

---

## 1. 引言

### 1.1 编写目的
本文档旨在明确 **OPC-Agent** 项目的需求边界、核心功能、用户场景、成本预算与风险管控策略，为 MVP 阶段（2周快速验证）及后续迭代提供统一的指引与决策依据。

### 1.2 背景概述
2026年，OPC（One-Person Company）模式在政策、资本与技术三重驱动下爆发，全国超 1200 万个体创业者以“个人决策 + AI 执行”模式运营。然而，OPC 创业者普遍面临任务过载、成本敏感、数据安全焦虑与系统运维困难等痛点。

本项目基于 **Harness 设计理念**、**Google ADK Go 框架**与 **Skill 渐进式知识管理机制**，为技术型 OPC 创业者构建一个可私有化部署、多 Agent 协作、按需加载技能的智能协助系统，用“单人+AI数字团队”的方式实现效率跃迁。

### 1.3 术语定义
- **OPC**：一人公司（One-Person Company），指借助AI智能体独立完成商业闭环的个人创业者。
- **Harness**：AI 驾驭系统，通过角色边界、状态机、产物契约、护栏规则四大要素约束智能体行为，确保稳定性与可控性。
- **ADK**：Agent Development Kit（Go 版本），Google 开源的多 Agent 编排框架。
- **Skill**：技能，采用 L1（发现）/L2（激活）/L3（引用）三级渐进式披露的知识模块。
- **Router Agent**：路由智能体，负责意图识别与任务分发。
- **HITL**：Human-in-the-Loop，人工确认机制。

## 2. 项目边界（范围）

### 2.1 包含的内容
**MVP 阶段（第1-2周）** 规定如下范围：

| 功能模块                 | 范围说明                                                     |
| ------------------------ | ------------------------------------------------------------ |
| **多 Agent 协作框架**    | 基于 ADK Go + 插件架构：Router Agent 内置，业务 Agent 以 Go Plugin (.so) 形式独立编译、运行时动态加载；MVP 包含文案生成、邮件分类两个插件 + 共享 Reviewer Agent |
| **Skill 渐进式加载**     | 文案生成 Skill（copywriting）、邮件分类 Skill（email_sorter）；通过 SkillToolset 统一加载，按需激活 L2/L3 |
| **Harness 核心要素落地** | 角色边界（Agent 职责限制）、状态机（执行步骤显式约束）、产物契约（结构化 JSON 输出）、护栏规则（禁止词、敏感操作 HITL） |
| **HITL 人工确认**        | 关键操作（如发送邮件、发布文案）以终端交互方式要求用户确认   |
| **本地运行环境**         | 单机运行，使用 ADK Web UI 调试，无需外部数据库服务           |
| **基础可观测性**     | 控制台打印状态机流转、错误日志，记录 token 消耗数据          |
| **Memory 长期记忆存储** | 轻量级向量记忆引擎：Agent 执行后将关键信息（用户偏好、历史决策、知识片段）生成 embedding 存储至本地文件；新任务启动时自动检索相关记忆注入 Agent 上下文 |
| **测试验证**         | 路由准确率、token 节省率、任务成功率等指标的定量测试         |

### 2.2 不包含的内容（MVP 阶段明确排除）
- **生产级向量数据库**：不引入 Postgres/pgvector 等外部数据库服务；MVP 阶段使用嵌入式内存引擎 + 文件持久化
- **多用户支持**：仅面向单一 OPC 创业者本人使用。
- **前端可视化界面**：仅通过 ADK Web UI 或命令行交互，不开发独立 Web 前端。
- **生产级部署**：不涉及 Docker 打包、Cloud Run 部署、CI/CD 流水线。
- **A2A 跨 Agent 通信协议**：MVP 内 Agent 间通过代码级调用完成，不引入 gRPC 或独立服务。
- **外部 API 集成**：不连接真实的支付、邮件发送或社交媒体接口，仅模拟执行。
- **复杂安全认证**：不做用户登录、权限分级。

### 2.3 后续迭代方向（MVP后扩展）
- 记忆存储升级：从嵌入式文件引擎迁移至 Postgres + pgvector，支持分布式持久化与更大规模检索
- 容器化部署与 Cloud Run 弹性伸缩
- A2A 协议与多语言 Agent 互操作
- **Agent 插件市场**：社区贡献的 Agent 插件按统一接口发布到私有/公开仓库，用户直接下载 .so 文件即可使用
- 更多业务插件（财务对账、竞品分析、代码审查等）
- 独立 Web 操作界面

## 3. 需求内容

### 3.1 功能性需求

| 编号 | 功能描述                                                     | 优先级 | 对应假设 |
| ---- | ------------------------------------------------------------ | ------ | -------- |
| F1   | 用户以自然语言输入任务，Router Agent 识别意图并路由至文案生成 Agent 或邮件分类 Agent | P0     | H1, H4   |
| F2   | 文案生成 Agent 根据 product name、卖点、风格，生成三段文案（短文案、长文案、社交媒体文案），输出 JSON | P0     | H2       |
| F3   | 邮件分类 Agent 分析邮件正文，输出类别（咨询/投诉/合作/垃圾）、理由和回复建议，输出 JSON | P0     | H2       |
| F4   | 两个业务 Agent 均以 Skill 形式封装，通过 SkillToolset 渐进式加载，上下文仅注入技能名称与简述，使用时才展开完整指令 | P0     | H2       |
| F5   | 每个 Skill 在 SKILL.md 中明确定义执行步骤（状态机）、输出格式（产物契约）、角色边界与禁止词（护栏规则） | P0     | H3       |
| F6   | Reviewer Agent 对业务 Agent 的输出按相应 Skill 的检查清单审查，给出评分，触发重试（最多一次） | P1     | H3       |
| F7   | 敏感操作（如“发送此邮件”、“发布这条文案”）在 Reviewer 通过后，调用 HITL 函数，要求用户在终端输入 y/n 确认；未确认前不得外部执行 | P1     | H3       |
| F8   | 系统在执行过程中以可读格式打印状态流转信息（Router→某Agent→Reviewer→HITL→Output） | P2     | H3       |
| F9   | 记录每次 Agent 调用的 token 消耗信息，便于人工统计           | P2     | H2       |
| F10  | Router 对无法识别的意图返回“unknown”，并提示用户重新描述     | P0     | H1       |
| F11  | Agent 每次执行完毕后，将任务上下文、关键决策、输出产物自动摘要并生成 embedding，写入本地记忆存储 | P1     | H2       |
| F12  | 新任务启动时，Router Agent 自动检索历史记忆中与当前任务语义相似的前 K 条记录（K=3~5），注入 Agent 上下文作为参考 | P1     | H2       |
| F13  | 系统通过 Go Plugin 机制加载 Agent：Agent 插件实现统一 AgentPlugin 接口，编译为 .so 文件，放入指定目录即可被主程序发现和加载 | P0     | H3       |
| F14  | 新增业务 Agent 时，开发者只需编写插件代码并独立编译，主程序无需重新编译；插件与主程序使用相同 Go 版本 | P0     | H3       |

### 3.2 非功能性需求

| 编号 | 需求             | 指标/约束                                                    |
| ---- | ---------------- | ------------------------------------------------------------ |
| NF1  | **响应时间**     | 单次任务（含 LLM 调用）最长时间 ≤ 30 秒                      |
| NF2  | **可靠性**       | 连续执行 20 次同类任务，成功率 ≥ 90%                         |
| NF3  | **路由准确率**   | 在 30 次测试中，Router 将任务正确分发到目标 Agent 的比率 ≥ 90% |
| NF4  | **Token 节省率** | 与无 Skill（全量指令注入）相比，使用 Skill 的基线 token 消耗下降 ≥ 60% |
| NF5  | **易维护性**     | 单个 Skill 的添加或修改仅需编辑目录中的文件，无需改动 Agent 核心逻辑 |
| NF6  | **可解释性**     | 状态机轨迹可被用户实时阅读，便于排查异常                     |
| NF7  | **资源占用**     | 本地运行内存峰值 ≤ 500MB，不消耗 GPU                         |

## 4. 用户故事

### 4.1 核心用户画像
- **姓名**：Alex  
- **角色**：独立 SaaS 开发者，以 OPC 模式运营一个小众效率工具。  
- **技能**：精通 Go 语言，有一定 LLM 应用开发经验。  
- **痛点**：每天需花 2-3 小时撰写产品推广文案、手动分类和回复客户邮件，压缩了产品研发时间。  
- **目标**：用 AI 助手自动处理这些重复性高、规则明确的业务任务，将时间重新投入产品迭代。

### 4.2 用户故事列表

| 编号 | 用户故事                                                     | 验收标准                                                     | 优先级 |
| ---- | ------------------------------------------------------------ | ------------------------------------------------------------ | ------ |

| US2  | 作为 Alex，我希望系统能自动识别客户邮件的类型并给出回复建议，这样我能更快处理用户反馈。 | 输入“这封邮件怎么办？‘产品坏了，我要退款’”，系统返回类别（投诉）、理由和回复草稿，并在“发送”前要求我确认。 | P0     |

## 5. 项目成本控制

### 5.1 成本构成估算

| 成本类别     | 细项                                     | MVP 阶段（2周）                      | 首年运营估算              |
| ------------ | ---------------------------------------- | ------------------------------------ | ------------------------- |
| **人力成本** | 1 名 Go 开发者（兼职，约 80 小时）       | 机会成本约 ¥16,000（按时薪 ¥200 计） | 后续迭代按需投入          |
| **基础设施** | 云服务器（2核4G，按需付费）              | ¥0（本地开发）                       | ¥3,000/年                 |
| **模型 API** | LiteLLM（Gemini Flash 或同等性价比模型） | 测试期间约 ¥100-200                  | ¥800-1,500/月（日常使用） |
| **工具服务** | GitHub 私有仓库、域名等                  | ¥0-100                               | ¥500/年                   |
| **总计**     |                                          | 约 ¥16,100-16,300                    | 约 ¥13,100-21,500/年      |

### 5.2 成本控制策略
- **模型选型弹性**：采用 Model-Agnostic 设计，支持 Gemini Flash、DeepSeek 等性价比模型，可根据预算随时切换；MVP 阶段优先使用免费额度或性价比最高的模型。
- **Skill 渐进式加载**：通过 L1 元数据发现、L2 按需加载，将 token 消耗降低 60%-90%，从源头控制 API 开支。
- **本地开发为主**：MVP 阶段完全在本地运行，不使用任何云服务，避免前期基础设施成本。
- **代码复用与开源依赖**：基于 Google ADK Go 开源框架，不依赖商业中间件；Skill 模板化设计可快速移植和复用，降低后续扩展开发量。
- **渐进式投入**：仅当 MVP 验证通过、业务价值确认后，才投入资源进行生产化部署和高级特性开发，避免过早过度设计。
- **记忆检索补益**：Memory 检索虽每次任务增加约 500-1500 tokens（K=5 条历史），但通过减少用户重复描述和避免 Agent 重复探索，预期整体 token 消耗仍净下降 10%-20%。

## 6. 风险控制与识别

### 6.1 风险识别矩阵

| 风险编号 | 风险描述                                              | 类别 | 影响(1-5) | 概率(1-5) | 风险等级 |
| -------- | ----------------------------------------------------- | ---- | --------- | --------- | -------- |
| R1       | ADK Go 框架 API 不稳定或文档缺失导致集成困难          | 技术 | 4         | 3         | 高       |
| R2       | LLM 输出格式不可控，JSON 解析失败频繁                 | 技术 | 4         | 4         | 高       |
| R3       | 大模型 API 延迟不稳定，响应时间超出 30 秒上限         | 技术 | 3         | 4         | 高       |
| R4       | Token 消耗未达预期下降，运营成本过高                  | 成本 | 4         | 3         | 高       |
| R5       | 意图分类不准，Router 将任务分发到错误 Agent           | 业务 | 3         | 3         | 中       |
| R6       | Agent 陷入死循环或越权操作，导致不可预测结果          | 安全 | 5         | 2         | 中       |
| R7       | 个人开发者因其他工作挤压，无法按时完成 MVP            | 进度 | 5         | 3         | 高       |
| R8       | Go AI 生态工具链不完善，缺乏成熟的最佳实践参考        | 技术 | 3         | 4         | 中       |
| R9       | 过于依赖 AI，用户自身业务能力退化或系统故障时业务停摆 | 业务 | 3         | 2         | 低       |
| R10      | 记忆检索引入错误历史上下文导致 Agent 输出偏差 | 业务 | 3         | 3         | 中       |

### 6.2 风险应对措施

| 风险编号 | 应对策略        | 具体措施                                                     |
| -------- | --------------- | ------------------------------------------------------------ |
| R1       | **缓解 + 应急** | 锁定 ADK Go v1.0 版本，优先参考官方 GitHub 示例；预留 20% 时间用于绕过框架 bug，必要时直接使用 Go 调用 LiteLLM API 实现部分功能。 |
| R2       | **预防 + 缓解** | 在 Skill 指令中强制要求 JSON 输出格式；代码层实现正则提取 JSON 块+重试逻辑（最多2次），并对常见错误进行模糊匹配修复。 |
| R3       | **缓解**        | 对 LLM 调用设置 context 超时（30秒），超时则触发用户重试提示；选择响应速度较快的 LiteLLM 后端。 |
| R4       | **主动控制**    | 早期进行 Token 对比实验（10个测试用例），根据结果调整 Skill 指令详细程度；若未达标，进一步压缩 SKILL.md 描述或切换到更便宜模型。 |
| R5       | **缓解 + 监控** | Router Agent 指令中明确分类边界，提供“unknown”兜底；补充少量样本做分类验证，统计准确率，必要时增加示例或细化分类。 |
| R6       | **预防**        | Harness 设计阶段明确护栏规则（禁止的操作清单）；实现 HITL 关键操作确认；Agent 指令中声明角色边界；代码层增加死循环检测（最大步骤计数）。 |
| R7       | **应急 + 缩减** | 制定严格的时间盒计划，按里程碑交付；若进度滞后，砍掉 Reviewer 自动审查等 P1/P2 功能，优先跑通最小闭环。 |
| R8       | **容忍 + 桥接** | MVP 阶段接受 Go 生态相对不成熟的现状；必要时通过 A2A（后期）或简单的 HTTP 调用桥接到 Python 服务处理特定任务。 |
| R9       | **认知转变**    | 系统定位为"数字员工"而非"完全替代"；关键决策、对外发布、财务操作始终保留人工终审；定期进行人工复盘 AI 输出质量。 |
| R10      | **缓解**        | 检索结果附带余弦相似度分数，低于阈值（如 0.7）的记录不注入上下文；每次注入时在提示词中标注"该信息来自历史记忆，相似度 x%，仅供参考" |
